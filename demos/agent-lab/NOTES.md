# 学习笔记

做这个项目时给自己的复盘，记下理解到的原理和踩过的坑。原理部分尽量用自己的话重述，避免照抄文档；踩坑部分全部是开发中真实发生的。

## Function Calling 到底是什么

最容易误解的一点：模型不会"运行"任何工具。它做的事情只是在学到 tools schema 之后，于合适的时机不输出普通文本，转而输出一段结构化 JSON，声明"我想调用 calculator，参数是 {"expression": "(3+4)*12"}"。真正执行这段调用的是浏览器里的 JS，执行完把结果包成 role:'tool' 消息发回去，模型再继续组织语言。

所以工具调用本质上是模型和执行者之间的一套协议，而不是模型的某种"能力"。这也解释了两件实践中的事：一是 tools 里的 description 字段极其重要，模型全靠它判断什么问题该用哪个工具，写得含糊调用就会跑偏；二是"执行"这一端可以是任何东西——本地函数、HTTP 接口、数据库查询，协议只关心结果以什么格式回传。

## SSE 的几个细节

流式输出用的是 Server-Sent Events 而不是 WebSocket，这是个经常被混淆的点。SSE 就是一段不结束的 HTTP 响应，消息帧之间用空行分隔，帧内 data: 行是负载，OpenAI 风格的流以 data: [DONE] 收尾。

浏览器自带的 EventSource 用不上的原因要记一下：它只支持 GET、不能设置 Authorization 头，而对话接口是 POST + JSON body + Key，所以只能 fetch 加 ReadableStream 手写解析。

实现中真正要小心的三处：一是网络包边界和帧边界不对齐，一个 data: {...} 可能被 TCP 拆成任意几段，解析器必须带缓冲区，这个行为可以写测试（把响应按 3 字节切块喂进去）；二是 TextDecoder 要开 stream 模式增量解码，中文的多字节序列被切断时普通解码会出乱码；三是流式工具调用的参数是分片下发的，id、函数名、arguments 都可能拆成多次到达，要按 index 累积拼接，拼错了拿到的就是残缺 JSON。

## Agent 循环与护栏

Function Calling 只完成一次工具请求，Agent 是在循环里反复执行"请求模型、执行工具、结果回传"这个流程，也就是 ReAct（Reason、Act、Observe）。写完之后我对 Agent 的理解可以压缩成：LLM 是决策器，工具是手脚，循环是骨架。

工程上有两个护栏不是可选项：maxSteps 限制循环轮数，模型可能陷入"调工具、对结果不满意、再调"的循环，不限次等于无限烧 token，我的实现到 8 轮就强制收手并如实告知；工具结果回传前做长度截断（4000 字符），防止一个失控的工具把上下文窗口撑爆。这两条在真实系统里对应的是成本控制和稳定性。

另外一个设计决定值得记录：runAgent 的 chat 和 execute 都是注入的依赖。这样循环逻辑的测试可以完全脱离网络，用假模型验证消息构造是否合法、护栏是否生效，测试速度快而且稳定。

## 错误处理的态度

工具执行被统一包成 {ok:true, value} 或 {ok:false, error}，永远不向上抛异常打断循环。失败信息原样回传给模型，让它决定换个参数重试还是向用户解释原因。我在浏览器里实测过这条链路：城市名解析错了，Open-Meteo 返回"未找到城市"，工具卡片显示失败详情，最终模型回复"抱歉，查询失败了"。Agent 系统的现实就是下游一定会失败，上层怎么兜住、怎么诚实地传达，比假装永不失败重要得多。

## 踩坑记录

这几条都是开发中真实发生的，按时间顺序：

1. 页面上凭空出现"nullnull"。原因是 replaceChildren(null, null)：DOM API 会把 null 静默转成字符串 "null" 插进去。条件渲染的节点必须先过滤再传。

2. 生成器里在 forEach 回调中写 yield，直接 SyntaxError。yield 不能跨函数边界，老老实实换 for...of。写流式分片函数时特别容易顺手写出来。

3. 工具失败的结构不统一。最初有的工具 return {error}、有的 throw，结果 executeTool 把 return {error} 也包装成了 ok:true，失败被当成了成功。教训是失败通道必须只有一条，最后统一改成：工具内部 throw，executeTool 统一 catch 并包装。

4. 正则贪婪匹配吞词。"北京现在天气怎么样"里的城市被提取成"北京现在"，因为表示时间的"现在"被一起捕获了。看似不起眼的解析函数也需要边界测试。

5. 最有价值的一个：Mock 服务器每轮的工具调用 ID 都从 call_mock_1 重新编号，结果第二轮的调用把第一轮的结果错配到了别的工具上——时间工具的返回被当成天气去解析，页面上出现一片 undefined。这让我真正理解了协议里 tool_call_id 存在的意义：它是把"模型请求的调用"和"回传的结果"关联起来的唯一钥匙。真实 API 生成全局唯一 ID 就是为了这个，一旦上下文里出现多处工具调用（多轮、并行），任何按 ID 关联的代码——结果回传、UI 卡片、日志追踪——都会被撞号击穿。
